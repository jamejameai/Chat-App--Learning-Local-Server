# Mini Telegram — Security Model & Hardening Guide

## 1. Security Architecture & Threat Model

Mini Telegram is built under the principle of **Defense in Depth** and **Zero-Trust Message Relaying**. The security design acknowledges that the self-hosted server runs in a home or private infrastructure environment where server-side physical or software vulnerabilities may exist.

### 1.1 Trust Boundaries

```
[ Unsecured Network / Internet ]
           |
           v
+------------------------------------------+
|  Reverse Proxy (Caddy / TLS 1.3 / OWASP) |
+------------------------------------------+
           | Internal Docker Network
           v
+------------------------------------------+
|  NestJS Modular Monolith                 |
|  - JWT Authentication Guard              |
|  - Role-Based Access Control (RBAC)      |
|  - Input Validation Pipe (class-validator)|
|  - Rate Limiting (Throttler)             |
+------------------------------------------+
           | Internal Docker Network (No Public Ports)
           v
+------------------------------------------+
|  PostgreSQL 16                           |
|  - Ciphertext message storage only       |
|  - Parameterized queries (Zero SQLi)     |
+------------------------------------------+
```

## 2. Authentication, Tokens & Identity Hardening

### 2.1 Password Hashing & Key Derivation
- Passwords (if enabled alongside invite keys) are hashed using **Argon2id** (memory: 64MB, iterations: 3, parallelism: 4) or **bcrypt** with a salt round factor of 12.
- Raw passwords and unhashed credentials are never written to disk, caches, or logs.

### 2.2 Short-Lived Access Tokens & Refresh Rotation
- **Access Tokens**:
  - Format: Cryptographically signed JWT (HMAC-SHA256 with 512-bit secret or Ed25519).
  - Lifetime: 15 minutes.
  - Claims: `sub` (User ID), `device_id` (Device UUID), `role` (`superadmin` | `member`), `exp`, `jti`.
- **Refresh Tokens**:
  - Lifetime: 30 days.
  - Storage: Stored as SHA-256 hash in `user_sessions` table.
  - Single-Use Rotation: Each refresh token exchange issues a new refresh token and immediately invalidates the previous one. If an invalidated refresh token is reused, all sessions associated with that device are revoked immediately (Token Reuse Detection).

### 2.3 Invitation Security Model
- **No Public Registration**: Registration is physically impossible without a cryptographically random, unexpired invitation code generated by the super-admin.
- **Invitation Token Generation**: Generated via cryptographically secure random bytes (`crypto.randomBytes(32)`), represented as a base64url or hex string.
- **Single-Use Enforcement**: Wrapped in a serializable database transaction:
  ```sql
  UPDATE invitations 
  SET used_at = NOW(), used_by_user_id = $1 
  WHERE token = $2 AND used_at IS NULL AND expires_at > NOW();
  ```
  If zero rows are updated, registration is rejected immediately.
- **Admin Revocation**: Super-admins can revoke invitations at any time before redemption.

## 3. Server Hardening & Infrastructure Protection

### 3.1 Network Isolation
- PostgreSQL, Redis (if used), and internal application micro-services run on private Docker networks without host port exposure (`ports:` directive is omitted in production Docker Compose; only the reverse proxy exposes port 443).
- Strict egress firewall rules prevent container escape network scans.

### 3.2 Rate Limiting & Denial-of-Service Defenses
- Applied globally and strictly tuned per route category:
  - Auth / Login / Invitation redemption: 5 requests per minute per IP.
  - API Mutations: 120 requests per minute per authenticated device.
  - WebSocket Message Submission: Max 20 messages per second per connection.

### 3.3 Protection Against Insecure Direct Object References (IDOR)
- Every query accessing a conversation, message, group, or attachment validates that the requesting `device_id` and `user_id` are active, authorized members of that exact entity.
- Changing IDs in URL paths or request payloads returns `403 Forbidden` or `404 Not Found`.

## 4. Local iOS Security

### 4.0 Live Location Privacy
- Location access is explained before the iOS permission prompt. OS permission alone never starts sharing; the user must explicitly start and can stop sharing at any time.
- Background sharing requires the user to allow Always location access. The app explains that sharing is visible only to friends explicitly selected for the current sharing session and includes a persistent stop control.
- The server stores one current coordinate per sharing account, with no route history. Read and realtime delivery require both an explicit session audience grant and a current mutual accepted friendship; adding a friend later does not grant access. Removing a friendship atomically removes its location grant; public/global presence never includes coordinates.
- Stopping sharing deletes the current coordinate and audience grants, then emits a stop event only to the selected audience and the owner's devices. Logout clears the server location before credentials are removed. A 256-bit stop-only capability is kept in the device Keychain and stored server-side only as a hash, allowing the app to revoke the share after its login session expires without granting any read access. Pending revocations are retried when the app starts and refreshes live locations. Coordinates are not included in push notifications.

### 4.1 Apple Keychain Protections
- Device Identity Keys, private Prekeys, and session JWTs are stored in the iOS Keychain using:
  - `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: Prevents extraction across device restores or iTunes backups.
  - Biometric constraint (`kSecAccessControlBiometryAny`) when Biometric App Lock is active.

### 4.2 SQLite Local Database Protection
- Local cache files are placed in the application container with file protection level:
  `FileProtectionType.completeUnlessOpen` or `complete`.
- The database is locked and unreadable when the iOS device is locked.

### 4.3 Biometric App Lock
- Implemented using Apple's `LocalAuthentication` framework (`LAContext`).
- Configurable timeout (Immediate, 1 min, 5 min, 15 min).
- System app switcher privacy shield: When the app moves to background (`sceneWillResignActive`), a privacy blur overlay is placed over the window to prevent previews in the iOS app switcher.

## 5. Notification Privacy (APNs)

Push notification payloads sent over Apple Push Notification service **NEVER** contain:
- Plaintext message text.
- Usernames or sender display names (configurable).
- Attachment keys or file hashes.
- Session tokens or authentication material.

### Default Push Payload:
```json
{
  "aps": {
    "alert": {
      "loc-key": "PUSH_NEW_MESSAGE_GENERIC",
      "loc-args": []
    },
    "badge": 1,
    "sound": "default",
    "mutable-content": 1
  },
  "c_id": "8a7c2931-...",
  "seq": 142
}
```
Upon receiving the push, the iOS client's Notification Service Extension connects locally, queries the backend using stored credentials, fetches the encrypted envelope, decrypts it locally, and presents the localized decrypted banner to the user.
